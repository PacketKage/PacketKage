# Internationalization (i18n)

PacketKage ships a full **English** and **French** experience across the React
frontend and the FastAPI backend. Locale selection is automatic and the app
degrades gracefully: an unknown or missing key falls back to English, so the
product never renders raw keys.

## Supported locales

- `en` — English (default)
- `fr` — French

Adding a third locale requires two dictionaries (`frontend` + `backend`), one
new entry in the locale registry, and (backend) a `resolve_locale` branch.

---

## Frontend

### Selection flow

1. A pre-paint `<script>` in `index.html` reads the saved preference
   (`localStorage['packetkage-locale']`) and sets the `lang` attribute.
2. `frontend/src/i18n/locale.ts` resolves the effective locale:
   saved preference → `navigator.languages` → `en`.
3. `LocaleContext.tsx` exposes `t` / `useT()` and a toggle that persists the
   choice and re-renders the tree.

### Key files

| File | Purpose |
|---|---|
| `src/i18n/dictionaries/en.json` | English catalog |
| `src/i18n/dictionaries/fr.json` | French catalog |
| `src/i18n/locale.ts` | `currentLocale`, `setCurrentLocale`, `normalizeLocale`, `translate`, `translateIn`, `interpolate`, `pluralSuffix` |
| `src/i18n/LocaleContext.tsx` | `useT()` hook + locale toggle |
| `src/components/ui.tsx` | Locale-aware `formatBytes` / `formatTime` / `formatDuration` |

### Conventions

- Keys use the dotted `page.section.message` scheme, e.g. `capture.detail.packets`.
- Placeholders interpolate with `{name}`; the special `{s}` marker renders the
  plural suffix for a `count` param (`pluralSuffix`).
- French pluralization: `count < 2` → no suffix, else `s`. English: `count == 1`
  → none, else `s`.
- `translate(key)` uses the active locale; `translateIn(locale, key)` pins one.
  Both fall back to the English entry, then to the key literal.
- Units are locale-aware: `formatBytes` uses `B/KB/MB/GB` (en) vs `o/Ko/Mo/Go` (fr).

### Requests

`src/api/client.ts` attaches `Accept-Language: <locale>` to every `fetch` call
and appends `?lang=<locale>` to query parameters, so the backend can localize
alert/report payloads per-request.

## Backend

### Selection flow

`GET /api/...` endpoints that return localized content accept:

1. `?lang=fr` query param (highest priority; `fr` → French, anything else en).
2. `Accept-Language` header — we only special-case `fr*`; everything else is en.

Resolution lives in `backend/app/i18n/__init__.py::resolve_locale`; the FastAPI
dependency is `get_locale`, injected as `locale: str = Depends(get_locale)`.

### Design: English persisted, French rendered at read time

Analysis always writes **English** alert content to the database. This keeps
existing captures valid and every stored row self-describing. Alongside the
English strings, the engine persists **stable message keys + params**:

```jsonc
{
  "title": "Port scan: 10.0.0.5 → 10.0.0.9 (44 ports)",
  "title_key": "alert.port_scan.title",
  "title_params": { "src": "10.0.0.5", "dst": "10.0.0.9", "n_ports": 44 },
  "reasons": [
    {
      "reason": "Distinct ports probed",
      "reason_key": "alert.port_scan.reason.distinct_ports",
      "detail": "44 unique ports on 10.0.0.9",
      "detail_key": "alert.port_scan.reason.distinct_ports.detail",
      "params": { "n_ports": 44, "dst": "10.0.0.9" },
      "weight": 30
    }
  ]
}
```

At read time `backend/app/i18n/localize.py` re-renders the French version from
`fr.json` (falling back to the stored English when a key is missing). When the
requested locale is `en`, the persisted payload is returned **untouched** —
byte-identical to pre-i18n output, which keeps the English-only test suite green.

### Key files

| File | Purpose |
|---|---|
| `app/i18n/en.json` | English catalog |
| `app/i18n/fr.json` | French catalog |
| `app/i18n/__init__.py` | `translate`, `resolve_locale`, `get_locale` (FastAPI dependency) |
| `app/i18n/localize.py` | `localize_alert` / `localize_alert_dict` / `localize_incident` |
| `app/services/suspicion_engine.py` | Emits English + keys/params per alert/incident |
| `app/api/alerts.py` `cases.py` `captures.py` | Locale-aware endpoints |
| `app/services/report.py` | `build_report(db, capture, locale)` |

### Key conventions

- `alert.<rule>.title` — alert title
- `alert.<rule>.explanation` — alert explanation
- `alert.<rule>.reason.<slug>` + `alert.<rule>.reason.<slug>.detail` — per-reason
  heading and detail
- `incident.title` / `incident.story` — correlated incident template
- `report.*` — HTML report chrome (headings, labels, column headers, footer)

`translate(locale, key, **params)` returns `None` when the key is absent so
callers fall back to the stored English rather than leaking a raw key.

### ORM / migrations

`AlertModel` gained four additive columns (enforced by `migrate.py`):

- `title_key` (TEXT), `title_params` (JSON)
- `explanation_key` (TEXT), `explanation_params` (JSON)

Reason-level keys/params are stored inline in the existing `reasons` JSON
column, so adding them required **no** schema change. `AlertRepository.create_many`
accepts the new dict keys because they map to real columns.

The special `data_exfiltration` rule has two explanation variants
(`explanation_first_contact` / `explanation_short`) chosen at analysis time based
on whether the destination was ever DNS-resolved.

### Tests

Backend English assertions continue to pass because locale resolution defaults
to `en`. French rendering is covered by `backend/tests/test_i18n.py` (API-level:
`Accept-Language: fr` returns French titles; `?lang=fr` report shows the French
heading).
